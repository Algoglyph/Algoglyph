# Pushdown Automata: Stack Memory & the Context-Free Class

## 1. Historical Context & Motivation

In **1959**, in the same Rabin-Scott paper that formalized finite automata, the authors introduced an extension: what if you give a finite automaton a **stack** (an unbounded last-in-first-out memory)? The result is a **pushdown automaton (PDA)** — a model strictly more powerful than DFAs but weaker than Turing machines.

The motivation came from **programming language parsing**. Noam Chomsky had shown (1956) that natural language syntax requires more than regular languages to model nesting and recursion — the language $\{a^n b^n : n \ge 0\}$ (balanced parens) is not regular. But full Turing machines are overkill for parsing. PDAs hit the sweet spot: enough memory to match parentheses, but constrained enough that membership is decidable in polynomial time (CYK, $O(n^3)$).

The landmark equivalence:

> **Theorem (Chomsky-Schützenberger, 1963).** The class of languages recognized by PDAs is exactly the **context-free languages** — the same class generated by context-free grammars (CFGs).

This duality is profound: the **generative** view (CFG, rules that build strings) and the **recognitive** view (PDA, machine that accepts strings) describe the same languages. Every compiler parser — `yacc`, `bison`, ANTLR, tree-sitter — implements a deterministic or nondeterministic PDA.

Today, PDAs model:
*   **Compiler parsers** (LR, LL, LALR parsers are deterministic PDAs)
*   **XML/HTML validation** (nested tag matching)
*   **JSON parsing** (nested object/array structure)
*   **Syntax highlighters** (incremental parsing)
*   **Protocol state machines** with bounded nesting (TLS handshake phases)

## 2. Core Mathematical Invariants

### Formal Definition

A **Pushdown Automaton (PDA)** is a 6-tuple:

$$M = (Q, \Sigma, \Gamma, \delta, q_0, F)$$

where:
*   $Q$ is a finite set of **states**
*   $\Sigma$ is the finite **input alphabet**
*   $\Gamma$ is the finite **stack alphabet**
*   $\delta : Q \times (\Sigma \cup \{\epsilon\}) \times (\Gamma \cup \{\epsilon\}) \to \mathcal{P}(Q \times (\Gamma \cup \{\epsilon\}))$ is the **transition function**
*   $q_0 \in Q$ is the **start state**
*   $F \subseteq Q$ is the set of **accept states**

A transition $\delta(q, a, b) \ni (q', c)$ means: in state $q$, read input symbol $a$ (or $\epsilon$), pop stack top $b$ (or $\epsilon$ = don't pop), then go to state $q'$ and push $c$ (or $\epsilon$ = don't push).

### Acceptance

A PDA accepts input $w$ if there exists a sequence of transitions starting in $(q_0, w, \epsilon)$ (state, remaining input, stack) and ending in $(q_f, \epsilon, \sigma)$ for some $q_f \in F$ and stack content $\sigma$. Some definitions accept by **empty stack** instead of final state; the two are equivalent in power. The concrete machine below uses both an accept state and an empty stack so its acceptance condition is explicit.

### The PDA-CFG Equivalence

> **Theorem.** A language is context-free $\iff$ it is recognized by some PDA.

**Intuition:** A PDA can simulate a leftmost derivation of a CFG by pushing the right-hand side of each production onto the stack, then popping terminals as they match the input. Conversely, a CFG can be extracted from a PDA by treating stack contents as nonterminals.

## 3. Step-by-Step Execution Trace

Let's trace the PDA above recognizing $a^n b^n$ on input `aabb`. The stack starts with bottom marker `$`, and the rightmost symbol is the top.

**Transitions:**
*   In $q_0$, read `a`, push `a`: stay in $q_0$.
*   In $q_0$, read the first `b`, pop `a`, and move to $q_1$.
*   In $q_1$, read each remaining `b` and pop one `a`.
*   In $q_1$, when the input is exhausted and `$` is on top, pop `$` and move to $q_2$ (accept).

**Trace `aabb`:**

| Step | State | Input | Stack (top → right) | Action                              |
|------|-------|-------|---------------------|-------------------------------------|
| 0    | $q_0$ | `aabb`| `$`                 | start with the bottom marker        |
| 1    | $q_0$ | `abb` | `$a`                | read `a`, push `a`                  |
| 2    | $q_0$ | `bb`  | `$aa`               | read `a`, push `a`                  |
| 3    | $q_1$ | `b`   | `$a`                | read first `b`, pop `a`, enter pop phase |
| 4    | $q_1$ | `ε`   | `$`                 | read second `b`, pop `a`            |
| 5    | $q_2$ | `ε`   | `ε`                 | pop `$`; **accept**                 |

**Result:** ACCEPT. The stack grew to height 2 (matching two `a`s), then shrank as we matched two `b`s.

**Trace `aab` (should reject):**

| Step | State | Input | Stack      | Action                          |
|------|-------|-------|------------|---------------------------------|
| 1-2  | $q_0$ | `b`   | `$aa`      | push one `a` for each leading `a` |
| 3    | $q_1$ | `ε`   | `$a`       | read `b`, pop one `a`             |
| 4    | $q_1$ | `ε`   | `$a`       | input is exhausted but `a` remains above `$`; no transition applies |

**Result:** REJECT. The bottom-marker transition is enabled only when all pushed `a` symbols have been matched and popped.

## 4. Production-Ready Implementations

### C++ (PDA Simulator)

```cpp
#include <bits/stdc++.h>
using namespace std;

struct PDATransition {
    int from_state;
    char input_char;    // 0 for epsilon
    char pop_char;      // 0 for epsilon (don't pop)
    int to_state;
    string push_str;    // pushed onto stack (leftmost char = new top)
};

class PDA {
    int numStates, start, accept;
    vector<PDATransition> transitions;

public:
    PDA(int n, int s, int a) : numStates(n), start(s), accept(a) {}

    void addTransition(int from, char in, char pop, int to, string push) {
        transitions.push_back({from, in, pop, to, push});
    }

    // Nondeterministic simulation via BFS over configurations.
    bool accepts(const string& input) {
        // Config: (state, input_pos, stack). Use string for stack.
        set<tuple<int, int, string>> visited;
        queue<tuple<int, int, string>> q;
        q.push({start, 0, "$"});
        visited.insert({start, 0, "$"});

        while (!q.empty()) {
            auto [state, pos, stack] = q.front(); q.pop();
            if (pos == (int)input.size() && state == accept && stack.empty())
                return true;
            // Epsilon transitions: try all matching.
            for (auto& t : transitions) {
                if (t.from_state != state) continue;
                // Case 1: epsilon input transition
                if (t.input_char == 0) {
                    if (t.pop_char == 0 || (!stack.empty() && stack.back() == t.pop_char)) {
                        string newStack = stack;
                        if (t.pop_char != 0) newStack.pop_back();
                        for (int i = (int)t.push_str.size() - 1; i >= 0; i--)
                            newStack.push_back(t.push_str[i]);
                        auto cfg = make_tuple(t.to_state, pos, newStack);
                        if (!visited.count(cfg)) {
                            visited.insert(cfg);
                            q.push(cfg);
                        }
                    }
                }
                // Case 2: consuming input
                if (pos < (int)input.size() && t.input_char == input[pos]) {
                    if (t.pop_char == 0 || (!stack.empty() && stack.back() == t.pop_char)) {
                        string newStack = stack;
                        if (t.pop_char != 0) newStack.pop_back();
                        for (int i = (int)t.push_str.size() - 1; i >= 0; i--)
                            newStack.push_back(t.push_str[i]);
                        auto cfg = make_tuple(t.to_state, pos + 1, newStack);
                        if (!visited.count(cfg)) {
                            visited.insert(cfg);
                            q.push(cfg);
                        }
                    }
                }
            }
        }
        return false;
    }
};

int main() {
    PDA pda(3, 0, 2);
    pda.addTransition(0, 'a', 0,   0, "a");
    pda.addTransition(0, 'b', 'a', 1, "");
    pda.addTransition(1, 'b', 'a', 1, "");
    pda.addTransition(1, 0,   '$', 2, "");
    pda.addTransition(0, 0,   '$', 2, ""); // accept n = 0

    cout << boolalpha << pda.accepts("aabb") << '\n'; // true
    cout << boolalpha << pda.accepts("aab") << '\n';  // false
}
```

### Python (PDA Simulator)

```python
from typing import Set, Tuple, List
from collections import deque

class PDA:
    """Nondeterministic pushdown automaton. Stack as a tuple of chars."""
    def __init__(self, start: int, accept: int):
        self.start, self.accept = start, accept
        self.transitions: List[Tuple[int, str, str, int, str]] = []

    def add(self, q_from: int, inp: str, pop: str, q_to: int, push: str):
        """inp/pop = '' for epsilon. push = '' to push nothing."""
        self.transitions.append((q_from, inp, pop, q_to, push))

    def accepts(self, input_str: str) -> bool:
        # BFS over (state, input_position, stack)
        start_cfg = (self.start, 0, ('$',))
        visited: Set[Tuple] = {start_cfg}
        q = deque([start_cfg])
        while q:
            state, pos, stack = q.popleft()
            if pos == len(input_str) and state == self.accept and not stack:
                return True
            for (qf, inp, pop, qt, push) in self.transitions:
                if qf != state: continue
                # Match input (epsilon or specific char)
                new_pos = pos
                if inp != '':
                    if pos >= len(input_str) or input_str[pos] != inp:
                        continue
                    new_pos = pos + 1
                # Match stack pop
                new_stack = stack
                if pop != '':
                    if not stack or stack[-1] != pop:
                        continue
                    new_stack = stack[:-1]
                # Push (leftmost pushed char = new top; we append in reverse)
                for ch in reversed(push):
                    new_stack = new_stack + (ch,)
                cfg = (qt, new_pos, new_stack)
                if cfg not in visited:
                    visited.add(cfg)
                    q.append(cfg)
        return False

# PDA for a^n b^n (final state plus empty-stack acceptance)
pda = PDA(start=0, accept=2)
pda.add(0, 'a', '', 0, 'a')   # push a for each a read
pda.add(0, 'b', 'a', 1, '')   # first b starts the pop phase
pda.add(1, 'b', 'a', 1, '')   # pop a for each b read
pda.add(1, '',  '$', 2, '')   # pop $, accept
pda.add(0, '',  '$', 2, '')   # accept n = 0
print(pda.accepts('aabb'))  # True
print(pda.accepts('aab'))   # False
```

## 5. Asymptotic Time & Space Complexity

| Model                        | Membership Time                | Space                       |
|------------------------------|--------------------------------|-----------------------------|
| **Deterministic PDA (DPDA)** | $O(n)$                         | $O(n)$ stack                |
| **Nondeterministic PDA**     | $O(n^3)$ (CYK / Earley)        | $O(n^2)$                    |
| **CFG (general)**            | $O(n^3)$ via CYK               | $O(n^2)$ table              |
| **LR(1) / LALR parser**      | $O(n)$                         | $O(n)$ stack                |

### The Determinism Question

A **DPDA** is a PDA where at most one transition applies in any configuration. DPDAs recognize a **proper subclass** of context-free languages called **deterministic context-free languages (DCFL)**. Examples:
*   $a^n b^n$ is a DCFL (the PDA above is essentially deterministic).
*   $\{ w w^R : w \in \Sigma^* \}$ (palindromes) is context-free but **not** deterministic — you must "guess" the midpoint.

The class DCFL is closed under complement, while CFL is not. This matters for parser design: deterministic parsers (LR, LL) are always linear-time, but they cannot handle all CFLs.

### The CYK Algorithm

For a general CFG in Chomsky Normal Form, the **CYK algorithm** fills an $n \times n$ table where cell $(i, j)$ contains the set of nonterminals deriving the substring from position $i$ to $j$. Each cell depends on $O(n)$ split points, giving $O(n^3)$ total time.

## 6. Systems Connections: How `yacc` Builds a PDA

### LR Parsing = DPDA

The `yacc`/`bison` toolchain generates an **LR(1)** parser — a deterministic PDA. The construction:

1.  **Write a CFG** in BNF notation with semantic actions.
2.  `bison` computes **LR(1) items** (sets of positions within productions, augmented with lookahead symbols).
3.  These items become the **states** of a DPDA. The stack holds state numbers and reduced nonterminals.
4.  The generated `yyparse()` runs in $O(n)$ — one shift or reduce action per input token.

The LR(1) automaton is a **deterministic pushdown automaton**. Conflicts (shift-reduce, reduce-reduce) indicate the grammar is not LR(1) — a practical signal that the grammar is ambiguous or needs refactoring.

### LL Parsing = Top-Down DPDA

An **LL(1)** parser is also a DPDA, but top-down: it predicts which production to apply before seeing the right-hand side. Recursive-descent parsers (hand-written) are typically LL(1). ANTLR generates LL(\*) parsers that look ahead adaptively.

### Why Not Just Use General CFG Parsing?

General CFG parsing (Earley, GLR) is $O(n^3)$ worst-case — too slow for production compilers parsing million-line codebases. Linear-time DPDAs (LR, LL) are the practical choice, accepting the restriction that the grammar must be in a decidable subclass.

### XML Validation

XML and HTML documents have nested tag structure: `<div><p>...</p></div>`. This is the language of balanced parentheses — a context-free language. Every XML parser maintains a stack of open tags, popping when it sees a closing tag. This is literally a PDA in action.

## 8. Frequently Asked Questions

**Q1: What's the difference between a PDA and a DFA?**
A: A DFA has **no auxiliary memory** — only a fixed number of states. It cannot count unboundedly, so it cannot recognize $a^n b^n$ (balanced parens). A PDA has an **unbounded stack**, allowing it to push symbols while reading one part of the input and pop them later to verify matching. This gives PDAs strictly more power: they recognize all context-free languages, a strict superset of regular languages.

**Q2: Can every PDA be converted to a CFG, and vice versa?**
A: Yes. The Chomsky-Schützenberger equivalence theorem proves this. **PDA → CFG:** the nonterminals of the CFG encode "the PDA goes from state $p$ with stack top $A$ to state $q$ with stack top $A$ popped." **CFG → PDA:** a single-state PDA simulates leftmost derivation by pushing the RHS of productions onto the stack and popping terminals as they match input. Both constructions are constructive and polynomial.

**Q3: What's the difference between a deterministic and nondeterministic PDA?**
A: A **DPDA** has at most one applicable transition per configuration — it never has to "guess." A **nondeterministic PDA** can have multiple applicable transitions and accepts if any branch leads to acceptance. DPDAs recognize **deterministic CFLs (DCFL)**, a strict subset of all CFLs. Example: palindromes $\{w w^R\}$ are CFL but not DCFL — you must nondeterministically "guess" the midpoint. LR(1) and LL(1) parsers are DPDAs, which is why they can't parse all CFGs.

**Q4: How is a PDA different from a Turing machine?**
A: A PDA has a stack with **LIFO access** — you can only read the top element. A Turing machine has a tape with **random access** — you can read any cell. LIFO access is restrictive: you can't "look deep" into the stack without popping everything above. This restriction makes PDAs strictly weaker than TMs. For example, $a^n b^n c^n$ (three balanced groups) requires comparing two counters — impossible with one stack, possible with a TM. The class hierarchy: Regular ⊂ Context-Free ⊂ Context-Sensitive ⊂ Turing-recognizable.

**Q5: Why do compilers use deterministic PDAs (LR/LL) instead of general CFG parsers?**
A: **Speed.** General CFG parsing (Earley, CYK) is $O(n^3)$ worst-case — too slow for million-line codebases. LR(1) and LL(1) parsers are deterministic PDAs running in $O(n)$. The trade-off: they can only parse grammars in the LR(1) or LL(1) subclasses, which excludes some valid CFGs (like inherently ambiguous ones). In practice, almost all programming language grammars can be rewritten to fit LR(1) or LL(1), making the linear-time guarantee worth the restriction.
